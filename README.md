# Restaurant Stop-List Bot

Serverless Telegram-бот для управления доступностью блюд, внутренними объявлениями и сменами сотрудников ресторана. Проект вырос из реальной рабочей задачи: заменить ручную передачу изменений единым актуальным источником данных.

## Что решает проект

- сотрудники меняют статус позиции: в продаже, ограниченное количество, ожидается или стоп;
- вся команда видит актуальный стоп-лист и получает уведомления об изменениях;
- поиск понимает названия блюд и распространённые рабочие сокращения;
- владелец управляет доступом, смотрит историю и статистику;
- команда работает с расписанием смен и объявлениями;
- повторно доставленное Telegram-событие не обрабатывается дважды.

## Архитектура

```text
Telegram Bot API
       │ webhook
       ▼
Cloudflare Worker ─── бизнес-логика и проверка доступа
       │
       ├── Cloudflare D1: меню, сотрудники, история, расписание
       └── scheduled trigger: открытие периодов и уведомления
```

Основные модули разделены по ответственности: `availability`, `broadcast`, `owner`, `schedule`, `orderParser`, `telegram` и `ui`. Схема базы создаётся последовательными SQL-миграциями.

## Технологии

- JavaScript, Node.js 22.13+ (для SQLite-тестов; проверено на Node.js 24)
- Cloudflare Workers и D1 (SQLite)
- Telegram Bot API и webhook
- SQL migrations
- встроенный тестовый раннер Node.js

## Локальный запуск

1. Установите зависимости: `pnpm install`.
2. Скопируйте `wrangler.example.jsonc` в `wrangler.jsonc` и укажите локальные значения.
3. Скопируйте `.dev.vars.example` в `.dev.vars` и добавьте тестовые секреты.
4. Создайте локальную базу: `pnpm db:local`.
5. Запустите Worker: `pnpm dev`.

Проверки:

```bash
pnpm check
pnpm test
```

## Развёртывание

1. Создайте D1-базу и внесите её идентификатор в локальный `wrangler.jsonc`.
2. Сохраните `BOT_TOKEN`, `WEBHOOK_SECRET` и `INTERNAL_SECRET` через Cloudflare Secrets; при необходимости добавьте `STAFF_CODE`.
3. Примените миграции: `pnpm db:remote`.
4. Опубликуйте Worker: `pnpm deploy`.
5. Передайте `BOT_TOKEN`, `WORKER_URL` и `WEBHOOK_SECRET` только через переменные процесса и запустите `pnpm telegram:setup`.

## Результат и безопасность

Автоматические проверки охватывают UI, отдельные правила доступа, расписание, формирование уведомлений, парсинг заказа, время и проверку webhook. Они не заменяют сквозную проверку с тестовым Telegram-ботом и Cloudflare D1. Конфигурация приведена в `wrangler.example.jsonc`; секреты задаются отдельно.

Рабочее окружение и данные сотрудников не входят в репозиторий.


## Обновление: разделение смен и надёжность доставки

- В записи за день выберите «Разделить смену», начало и конец перерыва, затем подтвердите результат. Например: 10:00–14:00 и 18:00–00:00. Общее начало и окончание берутся из существующей смены; обычная смена или выходной заменяют оба интервала.
- Сотрудник изменяет свою запись на следующую открытую неделю с четверга; менеджер и владелец также редактируют текущую открытую неделю. Общий график и личные уведомления показывают оба интервала.
- В управлении сменами доступна постраничная «История недель». Менеджер или владелец может удалить одну завершённую неделю со всеми её записями. Нажатие корзины открывает отдельное подтверждение. Текущие и будущие недели удалить нельзя.
- Подтверждения разделения и удаления привязаны к пользователю, чату и сообщению, действуют 10 минут и используются однократно. Изменённая запись или закрытая неделя блокируют сохранение разделения.
- Статус блюда, аудит и уведомление сохраняются одной транзакцией. Автоматическое снятие ожидания проверяет исходное время. Повторное событие, уже изменившее блюдо, не отменяет последующие изменения.
- Рассылка фиксирует доставки всех типов, повторяет временные ошибки по минутному cron и учитывает Telegram `retry_after`. Запрос API ограничен 10 секундами. Одна попытка обрабатывает до 35 адресатов; параллельные запуски ограничены арендой задания на 120 секунд. Тестовые уведомления остаются адресованными владельцу после включения рабочего режима.
- Маркер открытия записи, а также закрытие/повторное открытие будущей недели сохраняются транзакционно с уведомлением.

### Применение

Сначала сделайте резервную копию D1, примените миграцию `0008_reliability_split_shifts.sql` штатной командой миграций, затем разверните Worker. Существующие смены сохраняются без перерыва. Миграции 0001–0007 не менялись. Старые незавершённые рассылки отмечаются завершёнными: у прежней версии нет полных квитанций, поэтому их автоматический повтор мог бы разослать старые статусы. Новые задания обрабатываются очередью. Сохраните минутный cron из примера конфигурации.

Проверки: `pnpm check`, `pnpm test`; сборка без публикации: `pnpm exec wrangler deploy --dry-run --config wrangler.example.jsonc`. Интеграционные тесты используют встроенный `node:sqlite` с реальными миграциями и транзакциями, Telegram заменён тестовым ответом. Проверка реального Telegram и удалённой D1 требуется перед запуском в ресторане.

Гарантия доставки — с повторными попытками, а не строго однократная: при успешной отправке Telegram и сбое до сохранения квитанции возможен дубль. Временные ошибки остаются в очереди; следите за накоплением `notification_queue` и ошибками cron. Уведомления о ручных правках менеджера ставятся в очередь после записи смены; если именно постановка в очередь завершится ошибкой, бот сообщит о недоставленном уведомлении.
